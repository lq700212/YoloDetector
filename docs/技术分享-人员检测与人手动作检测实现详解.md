## 0. 一分钟看懂系统全景

一句话概括：**网络摄像头持续吐出视频画面 → 程序一帧一帧地"看图找 人"，再顺路分析每个人的手腕有没有伸进静电杆区域并停留足够久 → 把结论（红框、绿框、状态文字）画在画面上 → 显示到窗口**。

整条流水线长这样：

```
┌──────────┐   RTSP流    ┌───────────────┐  一帧图像(Mat) ┌──────────────────────────┐
│ 网络摄像头 │ ─────────▶ │ RTSP帧捕获器    │ ────────────▶ │ 检测管道（后台检测线程）        │
│ (工厂车间) │            │ RtspFrameCapturer│               │                          │
└──────────┘             └───────────────┘                │ ① YOLO 找出所有"人"(框)     │
                                                          │ ② 姿态模型找出每人的17个关键点│
                                                          │ ③ 规则引擎判定"是否在摸杆"    │
                                                          │ ④ 把框和文字画到这一帧上      │
                                                          └───────────┬──────────────┘
                                                                      │ 画好的图(Bitmap) + 结果快照
                                                                      ▼
                                                            ┌──────────────────┐
                                                            │ WinForms 主窗口    │
                                                            │ 预览区 + 日志面板   │
                                                            └──────────────────┘
```

对应到代码，一共三个线程在协作：

| 线程 | 代码位置 | 干什么 |
| --- | --- | --- |
| RTSP 捕获线程 | `Detection/RtspFrameCapturer.cs` 的 `CaptureLoop` | 不停从摄像头读最新一帧 |
| YOLO 检测线程 | `Detection/YoloDetectionService.cs` 的 `DetectionLoop` | 取最新帧做推理、规则判定、绘制 |
| UI 线程 | `UI/MainForm.cs` | 只负责显示图片和日志，不做任何计算 |

**记住一个核心思想**：抓帧、算、显示三件事速度差异巨大（抓帧快、推理慢、显示中等）。如果挤在一个线程里互相拖累，画面就会卡死。所以项目用"各干各的 + 只传最新数据"的方式解耦，后面第 6 章细讲。

## 1. 预备知识：几个必须认识的名词

| 名词 | 白话解释 |
| --- | --- |
| **RTSP** | 网络摄像头的标准视频流协议。给它一个地址（如 `rtsp://admin:密码@192.168.1.64/...`），就能像水龙头一样持续放出一帧帧画面 |
| **Mat** | OpenCV 库里的"一张图片"对象，本质是一块内存里的像素数组。本项目所有图像处理都以 Mat 为载体 |
| **YOLO** | 目前工业界最流行的目标检测模型家族。输入一张图，输出若干个**方框**，每个框带"这是什么类别 + 我有多确定" |
| **ONNX** | 模型的通用文件格式（类似照片界的 jpg）。训练好的模型导出成 `.onnx` 后，任何语言都能通过 ONNX Runtime 加载运行 |
| **推理（Inference）** | 把图片喂给模型、模型算出结果的过程。"跑一次推理" = "看一次图" |
| **置信度（Confidence）** | 模型对结果的把握程度，0~1。0.9 表示"九成确定这是个人" |
| **NMS（非极大值抑制）** | 同一个人常被好几个框同时框中，NMS 负责"留一个最准的，删掉其余重叠的框" |
| **关键点（Keypoint）** | 人体骨架上的定位点。COCO 标准定义了 17 个：鼻、眼、耳、肩、肘、**腕**、髋、膝、踝 |
| **ROI（Region of Interest）** | "重点区域"。本项目中指画面里静电杆所在的那块矩形区域 |

## 2. 人员检测是怎么实现的

实现类：`Detection/YoloV26Detector.cs`（约 400 行，建议对照阅读）。
一次检测分五步：**预处理 → 推理 → 解析输出 → 坐标还原 → 过滤去重**。

### 2.1 第一步：预处理——把任意尺寸的画面变成模型要吃的 640×640

YOLO 模型只认固定尺寸的输入（本项目为 640×640）。但摄像头画面通常是 1920×1080，直接硬缩放会把人压扁变形，影响精度。业界通用做法叫 **letterbox（信箱缩放）**：

```
原始画面 1920×1080                 模型输入 640×640
┌─────────────────────┐          ┌─────────────────────┐
│                     │          │ ░░░░░黑边填充░░░░░░░ │ ← padY
│      画面内容         │  等比缩小  ├─────────────────────┤
│                     │ ────────▶ │ │                   │ │
│                     │           │ │     缩小后的画面     │ │
│                     │           │ │                   │ │
└─────────────────────┘           ├─────────────────────┤
                                  │ ░░░░░黑边填充░░░░░░░ │
                                  └─────────────────────┘
                                    ↑ 保持宽高比缩放，上下（或左右）
                                      补黑边到 640，画面不变形
```

代码在 `YoloV26Detector.PreprocessMat`：

```csharp
scale   = min(640/宽, 640/高);        // 取较小的缩放比，保证整个画面装得下
padX    = (640 - 宽*scale) / 2;       // 左右剩余的空间平均补黑边
padY    = (640 - 高*scale) / 2;
```

除了缩放，还要做两件模型要求的"格式转换"：

- **通道顺序 BGR → RGB**：OpenCV 惯用 BGR 序，而模型训练时用的是 RGB 序，不转的话红色和蓝色互换，精度下降；
- **归一化**：像素值从 0~255 除以 255 变成 0~1，让模型输入数值范围稳定。

最终排成 `[1, 3, 640, 640]` 的张量（tensor）：1 张图 × 3 个颜色通道 × 640×640。

> **性能关键点（分享会高频考点）**
> 这一步最容易写慢。天真的写法是双重循环逐像素读 `Mat.Get<Vec3b>(y,x)`——每次调用都要跨过托管代码/native 代码的边界（P/Invoke），640×640 约 41 万像素 × 3 通道就是百万次跨界调用，实测一帧要 30~80ms。
> 本项目的做法：先用 `Marshal.Copy` **一次性把整块像素内存拷进 C# 字节数组**（只有 1 次跨界调用），再用单层循环填充张量——降到 1~3ms，提速约 20~30 倍。

### 2.2 第二步：推理——让模型"看图"

```csharp
using (var outputs = _session.Run(new[] { NamedOnnxValue.CreateFromTensor(inputName, inputTensor) }))
```

`_session` 是 ONNX Runtime 的推理会话，程序启动时加载一次模型（`Initialize` 方法），之后反复复用。**模型加载是秒级的，推理是毫秒级的**——所以绝不能每帧都重新加载模型（项目里模型实例跨启停会话复用，见第 6.4 节）。

模型输出一个大张量，里面是几千个"候选框"的信息。

### 2.3 第三步：解析输出——兼容两种格式

不同版本/导出方式的 YOLO 输出布局不一样，`ParseOutput` 按形状自适应（`YoloV26Detector.cs:136`）：

- **NMS 已做完的输出**（每行 ≤7 个数）：`[x1,y1,x2,y2,置信度,类别ID]`，直接就是角点坐标；
- **原始预测输出**：`[中心x,中心y,宽,高,obj分数,类别0得分,类别1得分,...]`，需要自己取最大得分的类别，坐标还可能是 0~1 的归一化值（判断依据：四个数全部小于 2 时乘以 640 还原）。

同时兼容 `[1,N,D]` 和转置的 `[1,D,N]` 两种维度排列。这样换任何一个 YOLO 系列 onnx 都不用改代码——只改配置文件里的模型路径即可。

### 2.4 第四步：坐标还原——把 640 空间的坐标变回原图

模型给出的坐标是在 640×640 输入图上的，必须逆运算回 1920×1080 原图，否则画出来的框位置全错。公式（**行为红线，现场调好的效果依赖它，不能动**）：

```csharp
// 模型输入空间 → 原图空间：先减掉黑边，再除回来时的缩放比
x' = (x_model - padX) * scaleX;
y' = (y_model - padY) * scaleY;

// 注意 scaleX/scaleY 是分别计算的（宽/scaledW、高/scaledH），
// 不能统一用 1/scale——因为 padX/padY 是整数截断的，两个方向误差不同
```

### 2.5 第五步：过滤去重——从几千个候选里留下最多 5 个人

一条流水线依次过滤（顺序有讲究）：

```
几千个候选框
   │ ① 类别过滤：TargetClassIds 默认只留 person(COCO id=0)，其余79类全丢
   │ ② 置信度过滤：低于阈值(Detection/yoloConfig.json 的 ConfidenceThreshold)丢弃
   │ ③ 边界裁剪：超出画面的部分裁掉；完全出界的丢弃
   │ ④ NMS：按置信度从高到低排队，逐个取出并与剩余的比 IoU（交叠率），
   │       重叠 ≥ 阈值的判为"同一个人的重复框"删除
   ▼
按置信度取前 5 个 → List<DetectionResult>
```

IoU（Intersection over Union）白话版：两个框的重叠面积 ÷ 合并总面积。1.0 表示完全重合，0 表示不相交。

之后还有一道**业务级后处理**（`DefaultResultProcessor`）：再裁一次边界 + 过滤小于 10×20 像素的碎框（噪声）。注意 ③ 在检测器内做过一次，这里是双保险，两处数值都是现场调好的。

**产出的数据结构**（`Detection/DetectionResult.cs`）非常简单：

```csharp
public class DetectionResult {
    public string ClassName;    // "person"
    public float Confidence;    // 0.87
    public float X, Y;          // 框中心点（原图像素坐标）
    public float Width, Height; // 框宽高
}
```

到这里，"人"已经找到了。接下来是本项目的特色功能：**人手动作检测**。

## 3. 人手动作检测（静电杆触摸）是怎么实现的

### 3.1 业务背景与技术选型

工厂防静电场景要求：工人接触电子元件前必须先触摸静电杆释放静电。系统需要自动判定**画面里的人是否正在触摸静电杆**。

选型思路（这是分享会上值得展开讲的架构决策）：

| 方案 | 问题 |
| --- | --- |
| ❌ 再训练一个"摸杆动作分类"深度模型 | 需要采集标注大量视频、部署重、结果是黑盒（为什么报/为什么不报说不清）、无法现场调整灵敏度 |
| ✅ **手腕关键点 + 区域几何规则** | 复用现有人体检测链路；判定逻辑完全可解释可调参（区域在哪、停留多久全在配置文件里）；换个车间只需重新标定一下区域 |

这就是"**AI 负责感知（找到手腕在哪），规则负责决策（手腕在不在该在的地方）**"的经典分工。

涉及三个类（均在 Detection 类库内）：

```
YoloPoseDetector      姿态模型推理：每人 17 个关键点坐标
EsdContactAnalyzer    规则引擎：跟踪每个人 + 接触状态机
EsdOverlayRenderer    叠加绘制：把结论画在画面上（见第 5 章）
```

### 3.2 YOLO-pose：从"框住人"到"找到手腕"

`Detection/YoloPoseDetector.cs` 加载的是另一个模型 `yolo11n-pose.onnx`（YOLO-pose 系列）。它和普通检测模型的区别：除了人体框，还额外输出每个人 **17 个 COCO 关键点**的位置和可信度：

```
        0鼻
    3耳 ○   ○ 4耳
  5左肩 ○─┬─○ 6右肩
         │
  7左肘 ○   ○ 8右肘
         │
  ★9左手腕○   ○10右手腕★  ← 我们只关心这两个！
         │
 11左髋 ○   ○ 12右髋
   ┌───┴───┐
 13膝○     ○14膝
   │       │
 15踝○     ○16踝
```

索引定义在 `CocoKeyPointIndexes` 常量表（`PoseResult.cs`），写规则时**禁止硬编码魔法数字 9/10**，要引用常量，防止以后换关键点数不同的模型时出错。

#### 为什么要"逐人裁剪小图推理"，而不是整帧直接喂？

这是本项目一个重要的工程取舍：

- **整帧推理的问题**：pose 全帧模式输出 8000+ 个候选，多人重叠时关键点容易张冠李戴（A 的手腕安到 B 身上）；且我们根本不关心画面里的人属于谁之外的信息。
- **逐人裁剪的做法**（`DetectSinglePerson`）：拿第一步人员检测的框 → 四周扩边 15%（防止贴边的肩膀/手腕被裁掉导致关键点丢失）→ 从原帧裁出单人小图 → letterbox 到 640×640 → 推理 → 只取分数最高的那一个候选（小图里基本只有一个人）。

```
整帧画面                        单人裁剪图（扩边15%）
┌────────────────────┐         ┌──────────┐
│  👤A    👤B    👤C  │  分别裁  ╱▒▒▒▒▒▒▒▒▒╲   对 A、B、C 各跑一次
│                    │ ──────▶ │▒  👤A   ▒│   小图推理（每次只看一个人，
│    静电杆 ▓▓▓       │         │▒        ▒│   关键点归属天然正确）
└────────────────────┘         └──────────┘
```

裁剪出的关键点坐标经过两级还原回到原图：`(模型坐标 - pad) / scale + 裁剪偏移量`。

**性能保护阀**：`MaxPersonsPerFrame = 8`。拥挤画面涌进几十人时，只对置信度最高的前 8 人做姿态推理，保证最坏情况耗时有上界；其余人返回空关键点（结果列表仍一一对应，不会错位）。

**兼容性设计**：模型输出的特征维（=5+3×关键点数，17 点即 56）在加载时从元数据探测，探测不到就等第一帧真实输出再判定——换 4 点/6 点/17 点的 pose 模型都不用改代码。

### 3.3 手腕落区判定：一个纯几何问题

拿到手腕坐标后，"是否在摸杆"就变成了初中数学题：**点是否在矩形区域内**。

静电杆区域（ROI）在 `Detection/esdConfig.json` 里用**归一化比例**标定：

```json
"RoiX": 0.40, "RoiY": 0.25, "RoiW": 0.20, "RoiH": 0.35,
"MarginPx": 20
```

- 用 0~1 的比例而不是像素值：换相机分辨率不用重新标定；
- `MarginPx = 20`：手腕点落在 ROI 外扩 20px 以内也算命中。关键点回归天然有几像素抖动，紧贴杆沿的触摸动作靠这个容差兜住。

判定条件（`EsdContactAnalyzer.IsWristInZone`）三者同时满足才算命中：

```
关键点存在 && 手腕置信度 ≥ 0.35 && 点在 ROI(外扩 MarginPx) 内
```

左手腕（idx 9）或右手腕（idx 10）任一命中，该人本帧记为"命中"。

### 3.4 跨帧跟踪：每一帧的人怎么知道是"同一个人"

检测结果每帧都是独立的，帧与帧之间模型并不知道"A 帧左边的人和 B 帧中间的人是同一个张师傅"。要做"持续触摸时长"统计，必须先把人**关联起来**。

本项目用最简单可靠的**贪心最近邻匹配**（`MatchTracksToPersons`）：

1. 每个被见过的人建立一条"轨迹"（Track），记录他上一帧人体框的中心位置，分配自增编号 TrackId；
2. 新一帧来了一批人体框，对每个人计算与所有轨迹中心的距离，**距离最近且小于"框尺寸×0.7"的轨迹判为同一人**（门限随人体大小自适应：人离镜头越近框越大，允许的帧间位移也越大）；
3. 匹配不上任何轨迹的，新建轨迹；
4. 超过 `TrackForgetMs`（3 秒）没人匹配的轨迹删除——**人走了再回来会重新计时**。

```
第10帧              第11帧               匹配结果
 👤#1                👤 #1(挪了一点)      位移 < 门限 → 还是 #1
    👤#2                 👤#2(没动)        就近匹配 → 还是 #2
                                          新出现的 👤 → 分配 #3
```

为什么不用更高级的跟踪算法（DeepSORT 等）？固定工位摄像头下人少、移动慢，近邻匹配已经足够可靠，还零依赖零成本。接口留好了，将来要升级随时可换。（容量保护：轨迹表上限 16 条，超出淘汰最久未更新的，防拥挤场景内存无界增长。）

### 3.5 接触状态机：从"这一帧碰了"到"正在触摸"

单帧命中不可靠——路过的人手扫过区域也就几十毫秒。真正有意义的信号是**持续接触**，所以用一个四态状态机（`EsdContactAnalyzer.UpdateStateMachine`）把瞬时命中累积成稳定结论：

```
                      ┌────────────────────────────────────────┐
                      │                                        │
   ┌──────────┐  命中   │  ┌──────────┐  累计≥HoldDurationMs(1.5s)▼
   │  空闲     │ ──────▶ │  │ 命中累计  │ ────────────────────▶ 【接触中 InContact】
   └──────────┘          │  └──────────┘                        │
        ▲                │   │ 手腕丢失                          │ 手腕丢失
        │ 超过宽限期       │   ▼                                 ▼
        │ (清零重来)      │  ┌──────────────────────────────────┐
        └────────────────┼──│ 宽限期 Grace(2s)：累计冻结不清零     │
                         │  │ 期间手腕回来 → 继续累计             │
                         │  └──────────────────────────────────┘
```

四个阶段对应防的就是四种真实世界的干扰：

| 参数（esdConfig.json） | 默认值 | 防什么 |
| --- | --- | --- |
| `HoldDurationMs` 持续认定 | 1500ms | **路人扫过**：手划过区域几十毫秒，远达不到 1.5 秒，不报 |
| `ReleaseGraceMs` 释放宽限 | 2000ms | **遮挡抖动**：摸着杆时手腕恰好被袖子挡住、关键点闪断一两秒，不断开、不清零 |
| `TrackForgetMs` 轨迹遗忘 | 3000ms | **离开重置**：人真走了超过 3 秒，删轨迹，回来重新计时 |
| `MarginPx` 判定容差 | 20px | **贴边误漏**：关键点坐标有几像素抖动，贴着杆沿也算摸到 |

状态机细节（都是实际踩坑修出来的，值得在分享会讲）：

- **时间累计基于真实时钟而非帧数**：命中帧累加的是"距上帧过了多少毫秒"（dt），所以就算开了降频（每 N 帧才分析一次，见 4.3）或者 RTSP 帧率波动，"1.5 秒"永远是真实的 1.5 秒；
- **dt 异常保护**：dt < 0（时钟回拨）或 > 5000ms（长时间卡顿后恢复）时按 0 处理，防止一次性灌入巨量时长造成瞬间误判；
- **结束事件携带最终时长**：退出接触态时先把累计值存起来再清零，否则日志永远打出"触摸持续了 0 秒"（开发中被测试用例当场暴露的 bug）；
- **单调时钟**：计时用 `Stopwatch` 而不是 `Environment.TickCount`——后者是 int 且约 49 天回绕，工控机连续运行跨天必炸。

### 3.6 输出：不可变快照

状态机每帧产出 `EsdFrameSnapshot`：当前每个被跟踪者的位置、左右腕是否落区、是否接触中、累计时长、总接触人数。它是**独立新建的对象**，外部随便持有修改都不会污染内部状态——这是本项目"事件传出的一律是不可变快照"铁律的体现（v1 曾因内部集合和事件参数共享同一实例导致外部修改污染内部状态的 bug，此后成为红线）。

## 4. 两者是怎么串起来的

### 4.1 一帧画面的完整旅程（核心时序）

前面两章的能力都汇聚在**同一个检测线程**的一条流水线上（`YoloDetectionService.ProcessSingleFrame`）：

```
检测线程拿到一帧 frame（原图 Mat）
│
├─ ① YOLO 人员检测        YoloV26Detector.Detect(frame)
│      → List<DetectionResult>（若干个人体框）
│
├─ ② 业务后处理            DefaultResultProcessor.Process(...)
│      → 边界裁剪 + 过滤 <10×20 的噪声框
│
├─ ③ ESD 旁路分析（可选）    RunEsdAnalysisIfEnabled(frame, detections)
│      ③a 姿态推理   YoloPoseDetector.Detect(frame, detections)
│                    → 每个人体框对应一份 17 关键点
│      ③b 状态机     EsdContactAnalyzer.Update(detections, poses, ...)
│                    → 更新跟踪/接触状态 → EsdFrameSnapshot 快照
│                    → 若某人状态翻转（开始/停止触摸）→ 触发 EsdContactChanged 事件
│
├─ ④ 发布结果快照          DetectionsUpdated 事件（给 UI 的统计面板用）
│
├─ ⑤ 画人员检测框          Visualizer.Draw(frame, detections)
│      → 红框 + "person 0.87" 标签（Skia 绘制，返回新 Mat）
│
├─ ⑥ 画 ESD 叠加层         DrawEsdOverlay(outputFrame)
│      → 黄色 ROI 框 / 绿色接触框 / 手腕徽标 / 统计行（OpenCV 原地绘制）
│
└─ ⑦ 发出成品帧            FrameProcessed 事件 → 编排层转 Bitmap → UI 显示
```

**注意 ① 和 ③a 的关系**：姿态检测**不需要再做一遍找人**——它直接拿 ① 产出的人体框当输入。这就是"串起来"的本质：

> **人员检测负责回答"人在哪"，姿态检测在"人在哪"的基础上回答"人的手腕在哪"，规则引擎在"手腕在哪"的基础上回答"他在不在摸杆"。三级接力，每一级只做增量工作。**

这也是当初选 pose 方案的隐藏红利：如果姿态模型自己也要全帧找人，等于每帧多做一次昂贵的人员检测；现在它只对现成的几个人框小图推理，又快又准。

### 4.2 "旁路"设计：附加功能绝不拖垮主业务

静电触摸检测在架构上是**可选旁路（bypass）**，三条防线保证它永远不会破坏人员检测这个主业务：

1. **未启用 = 零开销**：`YoloDetectionService` 的 `PoseDetector`/`EsdAnalyzer`/`EsdOverlay` 三件套属性任一缺失（比如 esdConfig.json 里 `Enabled=false`，或姿态模型文件不存在），整段逻辑直接 return，行为与纯人员检测完全一致；
2. **启动失败 = 降级不失败**：编排层 `VideoDetectionController.Start` 里 ESD 装配包在 try/catch 里——姿态模型损坏只记一条告警日志"已降级为纯人员检测"，预览照常启动；
3. **运行期故障 = 跳帧不停机**：每帧的 ESD 分析整体 try/catch，任何异常只记日志跳过本帧，下一帧照常，检测线程永不因此崩溃。

### 4.3 性能调节阀：降频分析

CPU 算力紧张时，`EsdProcessEveryNFrames` 可设为 2~3：每 N 帧才做一次姿态推理。跳过的帧沿用上次快照供叠加层显示。**为什么敢降频？** 因为接触时长基于毫秒时间戳累计（见 3.5），跟分析频率无关——1.5 秒的认定标准不因降频而失真。

### 4.4 事件出口一览（订阅关系图）

整条链路通过事件向外吐结果，UI 从不主动查询：

```
YoloDetectionService（检测线程内触发）
 ├─ DetectionsUpdated   : List<DetectionResult> 快照 ──▶ UI 统计展示
 ├─ FrameProcessed      : 画好框的 Mat ──▶ 编排层转 Bitmap ──▶ UI 预览
 ├─ EsdStatusUpdated    : EsdFrameSnapshot 快照（每帧，仅 ESD 启用时）
 └─ EsdContactChanged   : (trackId, 开始/结束触摸, 持续毫秒)
                           （仅状态翻转那一帧触发一次，不刷屏）
                              ──▶ UI 日志面板："⚡人员#3 正在触摸静电杆 (持续1.6秒)"
```

最后一条是报警/日志的正确姿势：**只在状态变化的那一帧发事件**，而不是每帧都喊一遍。订阅方（MainForm）收到后在后台线程回调里经 `SafeBeginInvoke` 调度回 UI 线程刷新界面。

## 5. 界面上的检测框是怎么画出来的

### 5.1 两层叠加绘制

界面上的画面其实是"三层合一"的结果：**原始帧 + 人员检测层 + ESD 叠加层**，全部在检测线程内画完才发给 UI：

```
原始摄像头帧（Mat）
   │
   ├── 第一层：人员检测可视化器（Visualizers/YoloBuiltinVisualizer.cs）
   │     红色 2px 描边框 + 红底白字标签 "person 0.87"
   │     绘制方式：Mat → SKBitmap → Google Skia 画笔绘制 → SKBitmap → Mat
   │
   └── 第二层：ESD 叠加层（EsdOverlayRenderer.cs，原地绘制不再拷贝）
         黄色矩形 + "ESD POLE"        ← 静电杆 ROI（现场标定的参考框）
         绿色粗框 + "#3 ESD OK 1.6s"  ← 正在触摸的人（接触态）
         灰色细框 + "#2 NO GND"       ← 在场但未触摸的人
         ●/○ 手腕徽标                  ← 人体框顶两角的小圆点：
                                          绿实心=该侧手腕已落区
                                          红空心=未落区（一眼看出哪只手差多少）
         左下角 "ESD: 1/3 in contact"  ← 全场接触统计行
```

两种绘制引擎并存是有意的性能选择：

- 人员框层走 Skia 位图往返（Mat→SKBitmap→Mat 约 5ms），换来抗锯齿的精细渲染；
- ESD 层用 **OpenCV 直接在 Mat 上原地矢量画**（矩形/圆/文字都是微秒级操作），省掉又一次位图往返约 10ms。预览帧是每秒几十张的大对象，能省一次拷贝就省一次。

### 5.2 标签为什么全是英文？

OpenCV 的 `PutText` 只支持 ASCII 字符，画中文会得到一堆"？"。模块内约定：**画面上的标签一律英文**（ESD OK / NO GND / person），中文提示放在 UI 日志面板（WinForms 控件原生支持中文）。

### 5.3 从 Mat 到屏幕：显示链路与资源交接

检测线程画完的 Mat 不能直接塞给 WinForms 控件（UI 层禁止接触 Mat，见 6.3），要经过一次边界转换：

```
检测线程                                    UI 线程
───────                                    ───────
outputFrame (Mat, 画好框)
  │ MatToSKBitmap()      ← SIMD 颜色转换+整块内存拷贝，1080P 约 5ms，像素零损失
  ▼
SKBitmap (跨平台位图)
  │ ToDrawingBitmap()    ← WinForms 只认 System.Drawing.Bitmap，整块拷贝约 0.5ms
  ▼
Drawing.Bitmap ──SafeBeginInvoke 跨线程调度──▶ ShowPreviewFrame():
                                                旧图.Dispose(); 换新图
```

两个易漏的细节：

- **旧帧必须 Dispose**：PictureBox.Image 被替换时，旧 Bitmap 不手动释放就成了等待 GC 回收的非托管内存泄漏。`ShowPreviewFrame` 里的 `old?.Dispose()` 就是干这个的；
- **调度失败就地释放**：窗体正在关闭时 `SafeBeginInvoke` 会失败，随行的 Bitmap 立刻就地释放，绝不让资源跟着失败的调度一起失踪。

### 5.4 为什么画面看起来是"实时"的？

检测一帧（含推理）通常几十毫秒，而摄像头 25fps 意味着每 40ms 就有一帧新画面——检测永远追不上生产速度。系统的答案不是加速，而是**主动丢帧**：检测线程永远只处理"最新的那一帧"，处理期间新到的帧覆盖缓冲区里的旧帧（单槽位缓冲，详见 6.1）。代价是高负载时丢掉一些中间帧，收益是**延迟恒定不累积**——你看到的永远是最近的画面，而不是几秒前的"录像回放"。

## 6. 支撑一切的工程细节

以下是分享会上最能体现深度的部分，全部来自实际踩坑。

### 6.1 三线程协作与单槽位缓冲

```
捕获线程 ────克隆帧────▶ ┌─────────┐ ────取走────▶ 检测线程
(RtspCaptureLoop)        │ 单槽位缓冲 │            (YoloDetectionLoop)
 生产快                   │ 只存最新一帧│             消费稍慢
                         └─────────┘
                       新帧到来时旧帧直接丢弃+Dispose
```

- 为什么不用队列攒着慢慢处理？推理 50ms、抓帧 40ms 时队列每秒净增 5 帧，几分钟就把内存吃满，而且处理的都是过期画面。**丢帧是有损但正确的策略**；
- 检测线程没帧时不空转烧 CPU：挂起等待（Monitor.Wait），新帧到达被唤醒（Pulse）。

### 6.2 线程停止协议（最容易写出崩溃的地方）

后台线程停止看似简单（设个标志位完事），实则暗雷密布。本项目沉淀的协议：

```
Stop(): volatile/锁内置停止标志 → Monitor.PulseAll 唤醒 → thread.Join(有界等待 3~10s)
```

- **为什么不用 AutoResetEvent/SemaphoreSlim？** WaitHandle 对象一旦在线程还活着时被 Dispose，线程再碰它就抛 ObjectDisposedException——v1 版本实际崩溃过。改用 Monitor.Wait/Pulse（纯锁机制，没有句柄可释放）后这类竞态从根上消失；
- **Join 超时怎么办？** 放弃等待让线程自行退出，**绝不在后台线程可能还在使用资源时去销毁那些资源**（比如 native 的 VideoCapture 可能正阻塞在一次 Read 里）。宁可慢退，不可崩退；
- **后台线程异常绝不逃逸**：两个工作循环整体 try/catch，记日志继续跑——一个网络抖动不允许弄死整条流水线。

### 6.3 Mat 所有权契约（内存不泄漏的关键）

Mat 包装的是非托管内存，GC 管不了它，忘一次 Dispose 泄一次。本项目立了一条铁律并贯穿全链路：

> **事件传出的资源归订阅者所有，用完必须 Dispose；每个环节 try/finally 终结自己的所有权。**

一帧 Mat 的完整生死簿：

```
CaptureLoop 读到 frame ─clone→ 发布 FrameReady ──▶ 编排层 OnFrameReady:
                                                    ProcessFrame(内部再克隆入缓冲)
                                                    finally: frame.Dispose() ①
检测线程从缓冲取走 ─推理─绘制→ outputFrame ─FrameProcessed─▶ 编排层:
                                                    转 SKBitmap/Bitmap 后立即
                                                    outputFrame.Dispose()    ②
Bitmap ──▶ UI 显示，替换时 old?.Dispose()                             ③
```

配套规则：UI 层永远只见 Bitmap 不见 Mat（想泄漏都没有入口）；"可能返回原对象"的方法（如 BGR 已是目标格式的 `ConvertToBgr`）调用方释放前必须 `ReferenceEquals` 判重，否则同一对象释放两次直接崩溃。

### 6.4 性能优化清单

| 优化点 | 天真做法 | 项目做法 | 收益 |
| --- | --- | --- | --- |
| 张量预处理 | 逐像素 `Mat.Get<>` 百万次 P/Invoke | Marshal.Copy 整块拷贝 + 单层循环填 CHW | 30~80ms → 1~3ms |
| Mat↔SKBitmap 互转 | JPEG 编解码中转 | 内存布局对齐（BGRA）+ Buffer.MemoryCopy 整块拷贝 | 10~30ms 且有损 → ~5ms 无损 |
| 显示转换 | — | SKBitmap→Bitmap 整块拷贝 | ~0.5ms |
| ESD 叠加 | 再走一次 Skia 位图往返 | OpenCV 原地矢量绘制 | 省 ~10ms/帧 |
| 模型加载 | 每次启停预览重新加载 | 检测器/姿态器实例跨会话复用 | 秒级 → 0（首次除外）|
| 姿态推理 | 整帧推理 | 逐人裁剪小图 + 人数上限 8 | 省算力 + 关键点归属正确 |
| ESD 分析频率 | 每帧 | 可配 N 帧一次，时长语义不受影响 | CPU 减负 |

### 6.5 配置体系：现场调参不动代码

所有需要"到了现场再调"的参数都在 JSON 配置里，改完重启即生效：

| 文件 | 管什么 | 典型调整场景 |
| --- | --- | --- |
| `Detection/yoloConfig.json` | 检测模型路径、置信度/NMS 阈值、可视化方案、调试日志开关 | 漏检→调低 ConfidenceThreshold；误检多→调高 |
| `Detection/esdConfig.json` | ESD 开关、姿态模型路径、ROI 标定、Hold/Grace/容差 | 换车间重新标定黄框；路人误报→加大 HoldDurationMs |
| `appsettings.json` + `cameraConfigs/*.json` | 激活的相机品牌、IP、RTSP 地址模板 | 换相机 |
| `Detection/model/*.onnx` | 模型本体 | 换更大更准的模型只改路径 |

设计原则：**检测模块自身不读任何配置文件**——宿主读好后经方法参数注入（如 `EsdConfig.ToOptions()` 转成 `EsdAnalysisOptions` 传进去）。这让整个 Detection 目录可以原样复制到别的项目使用。

### 6.6 分层架构一页纸

```
┌─ UI/MainForm ────── 纯界面：按钮、预览、日志（不碰 Mat、不算任何东西）
├─ App/Controllers ── 编排：装配链条、管理生命周期、终结 Mat 所有权
├─ Detection/ ─────── 检测域【独立类库 YoloDetector.Detection.dll】
│                     接口+实现齐备，零宿主依赖，整目录可搬走复用
└─ Cameras / Configuration / Infrastructure
                      相机品牌适配 / JSON 配置 / 文件日志
依赖方向严格单向：上层认识下层，下层不认识上层。
```

Detection 类库对外只暴露接口（`IYoloDetector`/`IPoseDetector`/`IFrameSource`/`IDetectionPipeline`...），实现可替换：换检测器、换可视化方案（配置里 `VisualizerType` 一改就从红框换成 OpenCV 绿框）、将来换帧源（比如本地视频文件）都不动其他层。

### 6.7 已知限制（诚实的技术债清单）

- RTSP 断流无自动重连：画面冻结但不崩溃，重连机制待加；
- 停止预览在网络假死时可能短暂阻塞（等 native Read 返回，有界等待保证最终能停）；
- 多人紧贴重叠时最近邻跟踪可能串人（TrackId 易主，触摸计时重算）；
- HIK/大华等品牌客户端未实现，工厂目前统一走 Angehua 协议。

### 7.2 分享会 FAQ 预演

**Q1：为什么识别"摸杆动作"不用深度学习分类模型？**
A：工业防静电的判定要素本来就是几何性的（手腕在不在杆上、停了多久）。规则引擎可解释、可现场调参、零训练成本；深度分类模型反而黑盒且要重新采集数据。AI 用在刀刃上——感知"手腕在哪"，决策交给规则。

**Q2：CPU 能跑吗？帧率多少？**
A：推理全部走 ONNX Runtime CPU（n 系列小模型）。即使检测耗时高于帧间隔，单槽位缓冲自动丢帧，画面依然是最新的，只是有效分析帧率下降。ESD 还有降频开关进一步减负。接触时长基于真实时钟，低帧率不影响判定准确性。

**Q3：两个人挨得很近会不会搞混？**
A：姿态层面不会——每人单独裁剪小图推理，关键点归属天然正确。跟踪层面可能串（近邻匹配的固有局限），后果是该人触摸计时重算，属已知限制，必要时升级 IoU+外观特征关联。

**Q4：程序开一天会不会越用越卡？**
A：内存安全是本项目的一级设计目标：Mat 所有权契约 + 事件快照 + 成对 Dispose + 97 个回归用例守护。计时用单调时钟防跨天回绕。理论上可无限运行（RTSP 断线场景除外，见已知限制）。

**Q5：怎么验证检测效果没被改坏？**
A：仓库自带回归体系（`.opencode/skill/全量回归验证/`，97 用例 + GUI 冒烟），其中包含用官方真实图片做的端到端对照（检出人数、关键点坐标与 Python ultralytics 基准一致）。改任何检测相关代码跑一遍即知。

**Q6：换个车间/换个相机要改代码吗？**
A：不用。标定 ROI 只需**在预览画面上按住鼠标左键拖一个框**（松手立即生效并自动保存到 esdConfig.json，运行期黄框即时移动到新位置；也可手改配置文件四个 0~1 比例值），再填上相机 IP、必要时调 HoldDurationMs——三个配置动作完成迁移。
